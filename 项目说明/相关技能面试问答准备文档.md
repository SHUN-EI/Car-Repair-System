#### 模块一：Agent 架构与编排

##### S1：LangChain

**一句话理解**：大模型应用开发的组件化框架，把模型调用、提示词管理、工具封装、上下文记忆这些重复劳动抽象成可复用模块，让开发者专注业务逻辑而不是胶水代码。

**追问 1：你们项目里 LangChain 具体承担什么？**
我们主要用它做三件事：统一的大模型调用入口，不同模型走同一套接口，换模型不动业务代码；提示词模板的集中管理，各智能体的提示词版本化维护；还有链式调用的基础封装。可以理解为它是我们项目的"模型访问层"。

**追问 2：LangChain 和 LangGraph 什么关系？**
LangChain 擅长线性的链式调用，但遇到分支、循环、条件跳转就力不从心。LangGraph 是它生态里的编排层，用状态图解决复杂流程控制。我们的分工很清晰：LangChain 管"怎么调模型"，LangGraph 管"流程怎么走"，两层各司其职。

**追问 3：LangChain 有什么不足？**
抽象层太厚，出问题时调试要穿透好几层封装；另外它的 Agent 抽象把流程控制权交给模型，确定性不够。所以我们的原则是**能用显式编排就不用隐式 Agent**，LangChain 只用它稳定的基础组件。

##### S2：LangGraph

**一句话理解**：基于状态图的智能体编排框架，把流程画成节点加条件边的图，每个节点是明确的处理步骤，状态在图里显式流转——它解决的核心问题是**让智能体的执行过程可控、可查、可测试**。

**追问 1：为什么选它不选其他方案？**
我们的场景是流程多分支且大量节点不需要模型。纯代码分支写多了难以维护，ReAct 式智能体又不可控。LangGraph 的状态图在中间：流程显式定义，条件边决定走向，循环和分支都是一等公民。而且图可以嵌套，主图挂子图，复用性很好。

**追问 2：你们项目怎么用的？**
三张图按业务域划分：问答图负责检索问答主线，机器人图负责钉钉消息的意图分发，工单导入图负责历史工单批量处理。图之间通过共享的检索层通信，不重复实现。条件边大量用规则判断，只有真正需要语义理解的节点才调模型。

**追问 3：怎么做错误处理和循环控制？**
每个节点可以定义失败出口，走降级边而不是中断；循环场景比如深度检索，设最大迭代次数防止死循环；整个图的状态可以快照，出问题能定位到具体节点。

##### S3：ReAct

**一句话理解**：让模型交替进行推理和行动的范式——先推理当前情况、决定采取什么行动、拿到行动结果再推理下一步，直到任务完成。它解决的是**单次推理解决不了、需要与外部环境多轮交互**的问题。

**追问 1：一轮循环具体怎么走？**
模型看到问题和之前的行动记录，输出一个动作决定，比如"换个方式再检索一次"；执行器跑这个动作，把结果追加到上下文；模型基于新信息再决定。我们给动作空间做了枚举约束，模型只能在预定义的动作里选，输出非法动作直接被规则拦下。

**追问 2：你们项目哪里用了？为什么不全用？**
用在深度检索救援：固定管道检索质量不达标时，才进入 ReAct 循环让模型自主换检索策略、改写查询词。不全用的原因是成本——每轮都过模型，延迟和费用线性涨，而且容易打转。我们的策略是**固定管道优先，ReAct 只做兜底救援**，设了最大轮数。

**追问 3：ReAct 最大的坑是什么？**
两个：一是循环失控，模型反复做无效动作，必须设迭代上限；二是上下文膨胀，每轮行动记录都追加，长了之后模型注意力分散。我们的处理是限制轮数加精简行动记录，只保留关键结论。

##### S4：Plan-and-Solve

**一句话理解**：先让模型把问题拆解成子任务计划，再按计划逐步求解，区别于 ReAct 的边想边做。它的价值是**全局视角规划，避免走一步看一步的局部短视**。

**追问 1：和 ReAct 怎么选？**
看两点：子任务之间有没有明确依赖、计划会不会中途失效。任务结构清晰、拆解后各干各的，用 Plan-and-Solve 效率高；任务依赖外部环境返回、计划容易失效，ReAct 或带反思的版本更合适。成本上规划一次就执行，比 ReAct 每轮都推理要省。

**追问 2：你们项目有两种落地形态？**
对。维修系统的专家模式是**静态版**：复合故障一次性拆解成单故障子任务，并行求解后分组合并，执行中不改计划——因为故障拆解结构相对固定，静态计划够用且延迟低。飞书助手是**带反思的完整版**：规划、执行、反思、综合四个阶段，反思不通过就重规划，最多三轮——因为办公任务依赖外部系统返回，计划容易失效。

**追问 3：静态版计划拆错了怎么办？**
这是静态版的固有代价，我们的补偿手段是子任务级别的救援——单个子查询求解质量差，会单独触发深度检索补救，而不是推翻整个计划。如果场景里计划失效是常态，就该升级成带反思的版本，这是演进方向。

##### S5：Function Calling

**一句话理解**：让模型决定"调哪个函数、传什么参数"的机制，但执行权始终在程序手里——模型只产出结构化的调用意图，真正的查询和操作由程序执行，结果再回传给模型组织回答。**模型是决策者，不是执行者**，这既是能力边界也是安全边界。

**追问 1：完整流程是怎样的？**
四步：把函数的名称、参数结构、用途描述随请求发给模型；模型理解意图后输出结构化调用指令；程序解析指令真正执行；结果回传，模型组织最终回答。

**追问 2：你们项目体现在哪？**
三处。最典型是深度检索循环：给模型定义枚举动作空间，每轮选动作加参数，执行器跑对应检索，结果回填——这就是 Function Calling 循环，用枚举加规则校验保证可控。其次是 MCP 工具层：检索、工单、库存能力封装成标准工具对外提供，MCP 本质就是标准化的 Function Calling 规范。第三是结构化输出：工单分析、知识抽取让模型按固定字段输出，程序解析后触发落库等业务动作。

**追问 3：为什么用枚举动作而不是原生接口？**
可控性。枚举加规则校验能拦住模型的非法输出，还能在模型不可用时降级成规则。原生接口省事，但企业场景我们优先确定性。

##### S6：多智能体协作

**一句话理解**：把复杂任务拆给多个专职智能体，每个只负责一件事，通过交接或分工协作完成整体目标。核心是**职责单一带来的可维护性**——哪一环效果差就单独优化哪一环。

**追问 1：你们项目有几种协作形态？**
两种。**流水线协作**：工单完成后的知识沉淀链路，分析智能体补全工单、抽取智能体生成知识条目、判重智能体比对去重，上一个的输出是下一个的输入。**分治协作**：专家模式里拆解角色把复合故障分成子任务，多个检索执行者并行求解，最后汇总角色分组组织回答——典型的主管加执行者结构。

**追问 2：为什么不做成一个大智能体？**
巨型提示词职责混杂，输出不稳定也没法单独优化。拆开后每个环节的提示词只服务一个目标，环与环之间还能插确定性校验——比如抽取结果缺字段直接打回，不用等到最后才发现。

**追问 3：智能体之间怎么协调一致性？**
靠契约不靠默契。交接的数据结构是预定义的，上游必须产出完整结构下游才接收；共享状态走统一的状态容器，不私下传递。出问题时看交接点的契约就知道是谁的责任。

##### S7：状态机编排

**一句话理解**：用显式的状态集合加转移规则来描述系统行为，任何时刻系统在什么状态、下一步能去哪都是确定的。它解决的是**复杂流程的可控性和可审计性**问题。

**追问 1：你们项目里有几层状态机？**
两层。**流程状态机**：LangGraph 的状态图，问答图的清洗、检索、过滤、精排每一步都是状态，失败走哪条降级边预先定义好。**业务状态机**：工单的完整生命周期，从草稿到归档十四个状态，转移白名单约束，非法转移直接拒绝。

**追问 2：状态机比 if-else 好在哪？**
三点：状态和转移显式声明，看定义就知道全部行为，if-else 散落在代码里；非法路径天然被挡住，白名单之外的转移根本不存在；每次转移可以统一挂权限校验和日志留痕，横切能力一处实现全局生效。

**追问 3：并发和重复事件怎么防乱？**
转移前校验当前状态，并发到达只有一个能通过状态检查；重复事件靠幂等键识别直接跳过。状态机本身就是并发防护栏，因为每一步都从"确认当前状态"开始。

##### S8：Agent 动态路由与任务分发

**一句话理解**：动态路由决定"这个请求交给谁处理"，任务分发决定"拆开的子任务怎么并行执行"。我们的设计原则是**按成本分级**——能用确定性机制解决的绝不用模型。

**追问 1：路由怎么分级的？**
三级漏斗。第一级规则路由：工单号格式、备件关键词命中直接分发，零模型成本；第二级分类路由：模型判断意图分到对应分支；第三级自主路由：深度检索里模型根据中间结果自己决定下一步动作。灵活性和成本成正比，贵的灵活性只留给真正需要的场景。

**追问 2：任务分发怎么保证可靠？**
以专家模式为例：子查询并行分发执行，整体设超时保护，超时用已有结果收口；任务级隔离，单个失败只影响自己那组；分发出去的任务必须有回收机制，不能让结果悬空。分发不只是发出去，还要管超时、隔离和回收。

**追问 3：加一个新意图要动多少代码？**
只加节点和分发规则，路由框架本身不动。这是我们用显式编排的回报——扩展是加法不是改法，回归测试的范围也小。

##### S9：MCP 协议与 MCP Server

**一句话理解**：模型上下文协议，把"模型怎么发现和调用外部工具"标准化了——工具的名称、参数、用途按统一规范声明，任何支持 MCP 的智能体都能即插即用地调用。它解决的是**工具接入碎片化**的问题，之前每接一个智能体平台都要单独适配工具格式。

**追问 1：和 Function Calling 什么关系？**
Function Calling 是模型侧的能力——模型能输出调用意图；MCP 是生态侧的标准——工具怎么注册、发现、描述、调用有了统一协议。可以理解为 MCP 是 Function Calling 的标准化和工程化，我们内部用动作空间实现调用机制，对外用 MCP 暴露工具能力。

**追问 2：你们开发了哪些 MCP 工具？**
把三类能力封装对外：知识检索、工单查询、备件库存查询。外部智能体接入后，模型侧就能按需调用我们的领域能力。这样检索这套核心逻辑被网页端、钉钉、MCP 三个出口复用，一套逻辑多端服务。

**追问 3：MCP 接口的安全怎么做？**
工具接口做了访问控制：凭据校验加来源限制，不是谁都能调。这是企业场景的基本要求——工具能查工单、查库存，等于开了数据出口，必须设门禁。

#### 模块二：AI 工具

##### S10：Dify 与 Coze

**一句话理解**：低代码智能体编排平台，通过可视化界面完成工作流搭建、知识库配置、模型接入，让不写代码或少写代码也能快速搭出可用的智能体应用。它们的价值是**验证快、交付快**，代价是深度定制受限。

**追问 1：两个平台的特点差异？**
Dify 偏工程化，支持私有化部署、工作流编排灵活，适合企业内部有数据不出网要求的场景；Coze 偏消费级，插件生态丰富、发布渠道多，上手更快但私有化能力弱。选型看数据敏感度和定制深度。

**追问 2：你们项目里怎么用的？**
主要用在需要快速交付和动态知识注入的场景：把外部接口和实时知识库封装好，通过低代码平台编排，推理时动态注入最新数据，解决静态模型时效性不足的问题。正式的核心业务系统还是代码开发，低代码平台做快速验证和轻量交付。

**追问 3：低代码平台和代码开发怎么选？**
我的判断标准是两个：定制深度和数据要求。流程标准、快速验证、接受云端托管，用低代码平台；流程复杂、要深度控制每个环节、数据必须私有化，用代码。两者不是替代关系，实际项目里经常混用——平台验证想法，代码承接核心。

##### S11：AI 编程助手

**一句话理解**：以 ClaudeCode、Codex、Trae 为代表的智能编程工具，覆盖代码补全、需求分析、代码生成、重构建议。它们的本质是**把开发者从重复性编码劳动里解放出来，让人专注设计和决策**。

**追问 1：你的实际工作流是怎样的？**
三个环节用得最多：需求拆解阶段让助手帮我梳理实现思路和边界情况，相当于一个随时的方案讨论对象；样板代码和测试用例交给它生成，我来审查修改；排查问题时把错误上下文给它做初步定位。核心原则是**它生成、我负责**——所有产出都经过人工审查才进代码库。

**追问 2：用这类工具最大的坑是什么？**
两个：一是幻觉——它会生成看起来正确但实际有隐患的代码，特别是依赖版本和边界处理；二是上下文缺失——它不了解你的项目约定，生成的代码风格不一致。我的对策是不盲目采纳、关键逻辑自己写、给它足够的上下文约束。

**追问 3：怎么衡量它带来的效率提升？**
我的体感是重复性工作的时间明显压缩，但更重要的价值在方案讨论——写代码前把思路跟它过一遍，能提前发现不少边界问题。效率提升不是"写得更快"，是"返工更少"。

#### 模块三：RAG 与知识检索

##### S12：非结构化文档解析

**一句话理解**：把 PDF、扫描件这类没有结构的文档转成干净、可切分的文本，是 RAG 的第一道工序——**解析质量决定后面所有环节的上限**，垃圾进必然垃圾出。

**追问 1：解析的难点在哪？你们怎么处理？**
三个难点：扫描版文档没有文本层，要过 OCR 识别；版面复杂有表格和页眉页脚，直接提取会混入噪声；不同来源格式五花八门。我们的处理是分层兜底：先试直接提取，失败走 OCR，解析结果做清洗和格式归一，每个文件独立处理互不影响。

**追问 2：文档怎么切分？**
两种策略按文档类型选：**章节感知切分**用于结构清晰的手册，按标题层级切，保证一个片段语义完整；**递归字符切分**用于普通文档，按大小递归切并保留重叠，避免切断上下文。切分粒度是权衡：太大语义混杂影响精度，太小丢上下文。

**追问 3：解析这一环你们踩过什么坑？**
历史工单扫描件质量参差，OCR 识别率不稳定。教训是**不要假设解析结果是对的**——导入的条目一律进待确认状态，人工确认后才生效，解析质量没保障的数据不能直接污染检索。

##### S13：向量化入库

**一句话理解**：把文本用编码模型转成向量存进向量数据库，让语义相近的内容在向量空间里距离相近，这是语义检索的地基。**入库质量决定召回上限**，精排再好也救不回没入库的内容。

**追问 1：向量库怎么选？**
我们选 Milvus，理由三点：分布式架构能扛库规模增长；索引类型丰富，可以按数据量调检索速度和精度的平衡；标量过滤支持好——我们的检索经常要按设备、状态这类字段先过滤再向量检索，这个能力是刚需。

**追问 2：什么时候同步向量？同步失败怎么办？**
知识发布的同时同步向量索引，保证"库里有就必然检得到"。同步失败会回滚发布状态，不出现"库里有条目但检不到"的不一致。这个事务性是我们知识闭环的关键设计。

**追问 3：向量的度量方式怎么选？**
我们用余弦相似度，关注方向不关注长度，对文本语义检索最合适。距离度量的选择要和编码模型的训练目标匹配，模型用什么训的，检索就用什么量。

##### S14：知识去重审核

**一句话理解**：新知识入库前的质量闸门——去重防止知识冗余互相打架，审核防止错误知识污染检索依据。**知识库是问答的根据，入口必须严**。

**追问 1：去重怎么做的？**
三层链从便宜到贵：先用故障码做确定性比对，零成本快路径；再用向量相似度筛出疑似重复的候选；只有高相似候选才交给模型判断故障原因和处理方案是否实质重复。设计原则是**保守不判重**——任何一层不确定就放行进审核，宁可人审多一条，不可误杀一条。

**追问 2：为什么相似度高不能直接判重？**
同一台设备同一个故障码，完全可能有两套不同处理方案——传感器问题和线路问题，标题几乎一样、相似度极高，但方案不同，这恰恰是最有价值的知识。相似度回答"像不像"，模型才能回答"是不是同一个知识点"。

**追问 3：为什么坚持人工审核加只读？**
错误代价不对称：一条错误知识入库会影响后续每次命中它的回答，错误被放大；审一条只要几十秒。只读是同样的逻辑——知识不能随手改删，每条进库的都有来源、有审核人，检索依据稳定了，回答质量才可归因。

##### S15：多路召回

**一句话理解**：用多种原理不同的检索方式并行召回再融合，因为**任何单路检索都有盲区**——向量的盲区是关键词的强项，反过来也一样，多路互补才能把漏检压到最低。

**追问 1：向量和关键词各管什么？**
向量管语义近似："电机嗡嗡响"能匹配"马达异响"；关键词管字面精确：错误码、型号这种没有语义的标识符，向量化后区分度差，必须靠字面匹配。我们的查询两类都有——口语描述是一类，直接报错误码是另一类，所以双路缺一不可。

**追问 2：几路？什么时候扩展？**
基础两路：知识向量召回加知识关键词召回。识别出设备错误码时扩成四路：加手册错误码精确匹配——等值查询是确定性路径，命中直接给最高权重；加手册日志码语义匹配。逻辑是**确定性信号出现就用确定性路径**。

**追问 3：多路召回的代价是什么？**
延迟和融合复杂度。延迟靠并行压缩，融合靠 RRF 解决分数不可比问题。我们的判断是：单路漏检的代价是多几个百分点的延迟，这笔账划算。

##### S16：RRF 融合

**一句话理解**：倒数排名融合，只看每路结果排第几名、不看分数——因为**不同检索路的分数根本不可比**，向量相似度和关键词得分放一起加权没有意义。

**追问 1：原理和参数？**
每条结果在每一路的名次贡献一个"1 除以常数加名次"的分数，各路相加。常数取 60 是经验值，作用是抑制头部名次差距——第一名和第二名的差距不该远大于第十名和第十一名。分数量纲问题被名次归一化天然解决，而且**双路都命中的结果天然排最前**，等于交叉验证。

**追问 2：融合时的去重怎么处理？**
这是我们踩过的坑：两个库的主键都是自增整数，融合时不同库的同编号条目被当成同一条互相覆盖。解法是构造复合标识——手册类条目加类型前缀区分来源库，同一条目被两路召回的用业务主键归并、分数累加。跨数据源标识冲突从此成了融合层的标准检查项。

**追问 3：为什么不训练一个融合模型？**
RRF 无参数、可解释、零维护成本，对我们的库规模完全够用。上学习式融合要标注数据、要防过拟合，收益不确定。**简单方案够用时，简单就是优点**。

##### S17：Reranker 精排

**一句话理解**：两阶段检索的第二阶段——粗排用双塔模型从大库圈候选，精排用交叉编码模型在小范围里精细排序。**双塔快但浅，交叉慢但深**，分工覆盖"大规模"和"高精度"两个矛盾需求。

**追问 1：交叉编码和双塔的本质区别？**
双塔是查询和文档各自独立编码成向量再算距离，文档向量能预计算，检索时只编码查询，所以快；代价是两者没有词级交互，语义理解浅。交叉编码把查询和候选拼在一起进模型做注意力交互，判断深得多，但每对都要现算，只能用在少量候选上。

**追问 2：精排多少条？挂了怎么办？**
头部三十条进精排、取前十进回答。三十条是效果和成本的平衡——融合后正确答案基本都在前列，再往后的候选翻不了盘。工程上候选分批送模型防输入过长、调用设超时、**精排只重排不过滤**。降级方案：精排服务不可用自动切规则加权重排，设备匹配的加权、多路命中的加权，效果降一点但功能连续，服务恢复自动切回。

**追问 3：精排能替代过滤吗？**
不能，职责分离。过滤是"该不该出现"的确定性问题——设备对不上就是不该出现；精排是"谁排前面"的排序问题。让精排干过滤的活会把两个问题搅在一起，出问题没法归因。

##### S18：跨语言检索与调优

**一句话理解**：查询和知识库语言不一致时的检索问题。我们的场景是英文设备日志查中文知识库。解法是**模型多语言能力打底、领域词表补强、兜底机制保底**三层叠加。

**追问 1：具体怎么解的？**
三层。第一层靠编码模型本身的多语言对齐能力，我们选的模型原生支持上百种语言，中英跨语言相似度是基本能力；第二层整理了英文故障术语到中文的映射词表，高频故障词先翻译再检索，兜住最容易失配的部分；第三层语义兜底，严格过滤后为空时放宽阈值再捞一次。

**追问 2：效果怎么验证？**
回归验证：优化前英文日志查询基本检不到东西，属于不可用；优化后稳定检到相关案例，且没有引入无关结果。这是典型的"从不可用到可用"的质变，比百分比更有说服力。

**追问 3：准确率调优的方法论是什么？**
一句话：**建验证集、跑回归、看分布**。从真实工单挑典型问题构造验证集，每次改动全量重跑，看正常查询是否放行、无关查询是否拦住；阈值看分数分布，相关和无关之间存在真空带就定在带中间。不拍脑袋，每个参数都能说出它卡在哪两类样本之间。

#### 模块四：模型微调与推理部署

> 本模块技能多为"了解"级别，回答按对应深度：概念清楚、场景清楚、实操讲经历不吹深度。

##### S19：LoRA 与 QLoRA

**一句话理解**：高效微调技术。LoRA 的思想是**冻结原模型权重，只训练旁路的小矩阵**——参数量降到原来的百分之一量级，单卡就能微调大模型；QLoRA 在 LoRA 基础上把基座模型量化加载，显存再降一截。

**追问 1：原理上为什么只训小矩阵就有效？**
微调的本质是让模型适配特定领域的表达方式，这种适配被认为是低秩的——不需要动全部参数，在注意力层旁边加一对小矩阵做增量修正就能实现。训练时只有旁路矩阵有梯度，推理时旁路可以合并回主模型，不增加推理开销。

**追问 2：你们实际怎么用的？**
在眼科问诊项目里，用 LoRA 对开源大模型做眼科领域微调，单卡完成训练。我负责的主要是数据侧——语料采集、清洗、脱敏、格式统一，配合训练框架完成微调流程。超参数层面了解秩、学习率这些关键项的作用，实操深度集中在数据工程这一环。

**追问 3：LoRA 和全量微调怎么选？**
看数据和算力。全量微调效果上限高但需要大算力和大数据量防过拟合；LoRA 适合算力有限、领域数据几千到几万条的场景，这也是大部分企业落地的现实选择。多领域切换时 LoRA 还有个好处——基座不变换适配器就行。

##### S20：垂直领域 SFT

**一句话理解**：用领域语料对模型做监督微调，让它内化特定行业的知识和表达规范。它解决的是**通用模型不懂行话、格式不规范、知识不够专**的问题。

**追问 1：你们眼科项目的完整流程？**
四步：数据侧从业务库和开源医学数据集多源采集，制定清洗规范做去重、脱敏、格式统一和异常剔除，构建训练集；训练侧用微调框架做 LoRA 微调；部署侧用推理引擎托管提供服务；验证侧用领域问题回归效果。我参与贯穿了数据构建和训练配置这两环。

**追问 2：微调语料最关键的是什么？**
我的体感是**质量和格式比数量重要**。医疗语料必须脱敏，一条没脱敏的数据就是合规事故；格式要统一成训练需要的对话结构，格式混乱模型学出来的输出也混乱；还有去重——重复样本会让模型过拟合特定表述。

**追问 3：微调效果怎么评估？**
领域问答回归：准备一批眼科典型问题，对比微调前后的回答专业性；另外看输出格式是否符合问诊规范。诚实说，医疗场景我们没有自动化评测分数，主要靠领域问题的抽样人工评估，这也是垂直领域微调的普遍现状。

##### S21：LLaMA-Factory

**一句话理解**：一站式大模型微调框架，把数据加载、训练方法、量化、评估、部署这些环节统一封装，通过配置就能跑通主流微调流程，**大幅降低微调的工程门槛**。

**追问 1：为什么选它？**
三个理由：支持的训练方法全，LoRA、QLoRA、全量微调都有，换方法改配置就行；对主流开源模型适配好；数据格式规范清晰，我们的语料整理成它要求的格式即可。对中小团队来说，它把微调从"研究项目"变成了"工程任务"。

**追问 2：用它微调的关键配置有哪些？**
训练方法选 LoRA，精度用 BF16，数据指向清洗好的语料，学习率和轮数按数据规模调。我们的经验是轮数不宜多——领域数据规模有限，轮数多了过拟合，回答开始复读训练样本。

##### S22：vLLM

**一句话理解**：高性能大模型推理引擎，最初为生成式推理设计，核心优势是**高吞吐**——通过显存分页管理消除生成过程 KV cache 的碎片浪费、连续批处理把不同请求动态拼批。后来扩展成通用模型服务框架，支持编码和重排模型托管，是私有化部署的主流选择。

**追问 1：为什么推理要用专门的引擎而不是直接加载模型？**
直接加载是逐条处理请求，并发一来要么排队要么显存爆。推理引擎做了两件关键事：显存的精细管理，避免碎片化浪费；请求的动态拼批，不同长度、不同阶段的请求合并计算。这两点对吞吐的提升是量级上的。

**追问 2：你们怎么部署的？**
维修系统里，编码模型和精排模型统一用推理引擎托管在独立推理服务，对外提供兼容主流格式的接口，业务侧只认接口不认模型——换模型、升版本改部署配置就行，业务代码零改动，这个解耦我们实际受益过。眼科项目里同样用它托管问诊模型，配合接口层对外提供服务。

**追问 2.5：vLLM 不是为生成设计的吗，托管编码模型有什么价值？**
这个边界我们选型时清楚：PagedAttention 解决的是生成时 KV cache 的显存管理，编码模型是单次前向用不到。编码模型受益的是服务框架能力：请求级拼批、显存统一调度、标准化接口。选它统一托管三类模型，图的是一个引擎、一套接口、一套运维。编码侧将来真遇到瓶颈，可以换专门的编码推理服务，接口层不用动。

**追问 3：推理服务挂了怎么办？**
服务带健康检查，加载中、就绪、异常状态分开上报；上游按状态决定等待还是降级——我们的检索链路在编码服务不可用时自动切纯关键词召回，功能不中断，恢复后自动切回。

##### S23：全链路降级兜底机制（了解级）

**一句话理解**：让系统在依赖出故障时仍能提供有损但正确的服务，三个核心手段：**回退**——切换到更便宜的替代方案；**重试**——瞬时故障自动再试；**安全闸门**——宁可拒绝也不输出错误结果。

**追问 1：你们项目的降级是怎么设计的？**
原则是每一环都有替代方案且切换自动完成：编码服务不可用，检索降级成纯关键词召回；精排不可用，切规则加权重排；检索结果为空，有语义兜底放宽阈值再捞；分类意图失败，有规则兜底。恢复也自动——每次调用探测服务状态，恢复后下一次调用自动切回。

**追问 2：降级设计最重要的原则是什么？**
**降级后的行为必须仍然是正确的，只是质量下降**。绝不能为了看起来可用而返回错误结果——宁可回复"未检索到"，不能降级成编造答案。这条在我们回答层的护栏上体现得最直接：没有可信案例就固定话术拒绝回答，模型根本不参与。

**追问 3：安全闸门具体怎么实现的？**
以回答层为例：检索结果为空或最高分低于可信阈值时，确定性逻辑直接拦截，不调用模型，返回固定话术。把"能不能回答"的决定权放在确定性代码里而不是提示词里——可控性靠链路设计保证，不靠约束模型。

#### 模块五：后端开发与系统集成

##### S24：FastAPI 异步服务

**一句话理解**：Python 的现代异步 Web 框架，基于异步语法实现高并发，自带接口文档和数据校验。它的价值是**用 Python 的开发效率拿到接近异步模型的并发能力**，特别适合 IO 密集的大模型应用。

**追问 1：为什么异步对大模型应用特别重要？**
大模型应用的瓶颈在等待——等模型推理、等向量库、等外部接口，都是 IO 等待。同步模型里等待时线程干耗着，异步模型里等待时事件循环去处理别的请求，同样的并发量资源消耗差很多。我们的问答接口背后要串检索、精排、生成好几次外部调用，异步是必然选择。

**追问 2：流式输出怎么实现的？**
用服务端推送事件的方式：回答边生成边分段推给前端，每段带事件类型，前端按类型渲染思考过程、引用来源、正文。用户感知的等待时间从"等完整回答"变成"马上看到内容开始动"，体验差异很大。

**追问 3：和 Django 这类框架比怎么选？**
Django 全家桶适合传统业务系统，我们这种以接口为主、前端分离、强依赖异步的场景，FastAPI 更轻更合适。框架选型看场景，不看流行度。

##### S25：JWT 鉴权

**一句话理解**：无状态的令牌鉴权机制——登录成功后服务端签发一个带有效期和身份信息的签名令牌，之后每次请求带令牌，服务端验签即可确认身份，**不需要在服务端存会话**。

**追问 1：完整流程？**
登录验证通过后签发令牌，里面带用户身份和过期时间，用密钥签名；请求到达时验签加查有效期，通过则放行并解析出身份；过期了重新登录或走刷新机制。签名保证令牌不能被伪造篡改，这是安全的基础。

**追问 2：无状态的优缺点？**
优点是横向扩展容易，任何服务实例都能验令牌，不依赖共享会话存储，对我们多容器部署很友好。缺点是签发出去的令牌在过期前无法主动作废，所以有效期要设短，敏感操作配合其他校验。另外令牌只放身份标识不放敏感信息，因为它只是签名不是加密。

**追问 3：你们项目哪些场景用了？**
飞书助手项目的接口鉴权用 JWT，配合三级角色模型做权限判断。维修系统里开放给外部调用的工具接口走的是凭据加来源校验——不同出口按安全等级选不同机制，不一刀切。

##### S26：限流与访问控制

**一句话理解**：限流是控制单位时间请求量的保护机制，常见实现有令牌桶和滑动窗口——前者平滑允许突发，后者精确统计区间内总量。它解决的是**保护后端不被突发流量或恶意请求打垮**。

**追问 1：你们项目怎么做的？**
我们的保护重点是**访问控制加资源防护**两层。对外暴露的工具接口做凭据校验加来源限制，不是合法调用方根本进不来；对模型这类昂贵资源，靠意图路由把大量无效请求拦在模型调用之前，加上缓存减少重复计算——本质上都是"把不该消耗的资源消耗挡在门外"。

**追问 2：如果并发再上一个量级怎么扩展？**
两个方向：接入层加标准限流，按令牌桶控制单用户速率；模型侧靠推理引擎的批处理削峰，排队加异步化，把瞬时峰值摊平。这块我们做过设计评估，当前业务量级下访问控制加缓存已经覆盖。

##### S27：统一异常处理

**一句话理解**：在全局层面统一捕获和转换异常，对外输出格式一致的错误响应，**让调用方拿到可预期的错误信息，而不是原始堆栈或静默失败**。

**追问 1：你们怎么实现的？**
三层：框架层的全局异常拦截，把未捕获异常转成标准错误格式，生产环境不暴露内部堆栈；业务层的主动校验，比如工单状态流转不合法直接返回明确的业务错误码和原因；依赖层的降级处理，外部服务异常走降级逻辑而不是向上抛。三层的边界是：**能降级的降级，不能降级的给明确错误，绝不静默吞掉**。

**追问 2：异常处理和降级的关系？**
降级是异常处理的一种策略。我们的判断标准是这个异常影响的是质量还是正确性——影响质量的走降级继续服务，影响正确性的明确拒绝。比如精排挂了降级规则重排，但工单非法流转必须拒绝，降级不得。

##### S28：MySQL

**一句话理解**：最主流的关系型数据库，以事务、索引、成熟生态见长，承载结构化业务数据。在智能体应用里它管的是**确定性的那部分数据**——用户、工单、审批记录这些需要强一致的内容。

**追问 1：你们项目怎么用的？**
飞书助手项目用关系库加轻量库的组合承载业务数据，Text2SQL 场景下，自然语言查询转成 SQL 在业务库上执行，并自动注入部门过滤条件保证数据隔离。维修系统的主业务库用的是 PostgreSQL，因为要用它的模糊检索扩展做关键词召回这一路——选库看场景需求。

**追问 2：Text2SQL 怎么防注入和越权？**
两道闸：生成的查询只允许只读操作；查询自动注入调用者的部门过滤条件，**权限过滤在服务端强制完成，不信任模型生成的语句**。

**追问 3：索引这块你的理解？**
查询条件建索引、覆盖索引减少回表、注意最左匹配和选择性——高频查询先看执行计划再决定加什么索引。我们在关键词检索路上就专门建了文本检索索引，查询性能提升是数量级的。

##### S29：Redis

**一句话理解**：内存键值数据库，以极低延迟提供缓存、计数、分布式锁等能力。在智能体应用里它的角色是**把贵和慢的操作变便宜变快**。

**追问 1：你们项目用在哪些场景？**
三类：**会话缓存**——多轮对话的上下文存内存库，设过期时间自动清理，不占业务库；**高频数据缓存**——设备码表这类读多写少的数据短时效缓存，避免每次检索都查库；**幂等控制**——审批同步这类事件场景用唯一键识别重复事件，防止同一审批落库两次。

**追问 2：缓存怎么保证不过期数据害人？**
短时效加容忍度设计：我们缓存的都是允许短暂不一致的数据，码表这类就算缓存滞后几秒也没业务影响。真正需要强一致的数据不走缓存直接查库。**缓存的边界是按数据的一致性容忍度划的**。

**追问 3：Redis 挂了影响什么？**
会话要重新建立，缓存降级成直接查库，幂等控制退回数据库唯一约束兜底。功能不受损，只是部分请求变慢——这也是为什么它适合放非关键路径。

##### S30：Milvus

**一句话理解**：分布式向量数据库，专为大规模向量的存储和相似度检索设计，支持多种索引和标量过滤。它解决的是**向量数据规模上来之后，通用数据库扛不住检索性能**的问题。

**追问 1：为什么不用 PG 的向量插件或者 FAISS？**
我们的选型考虑三点：库规模会随工单持续增长，需要分布式扩展能力；检索经常要"按设备过滤再向量检索"，标量加向量的混合查询是刚需；生产环境要高可用和运维生态。轻量场景用插件够了，但企业级检索系统我们选专用库。

**追问 2：索引怎么配的？**
用倒排聚类类索引，检索时只扫描部分聚类换取速度，聚类数量和扫描范围按库规模调过——这是速度和召回精度的经典权衡，我们拿验证集测出当前规模下的合适配置。

**追问 3：向量同步的一致性怎么保证？**
知识发布和向量写入绑定，写入失败回滚发布状态，保证"库里有就必然检得到"。双集合设计按数据类型分开管理，检索时按类型路由。

##### S31：Docker Compose

**一句话理解**：多容器编排工具，用一个声明式文件描述所有服务、依赖和配置，一条命令起停整套环境。它解决的是**环境一致性和部署复杂度**问题——开发、测试、生产跑的是同一套定义。

**追问 1：你们的编排结构？**
入口是反向代理，后面两类服务：主应用提供接口和静态页面，推理服务独立成组单独扩缩容；数据面是关系库、向量库、缓存三个有状态服务，数据卷独立挂载。配置走环境变量注入，同一套镜像多环境复用。

**追问 2：为什么不用 K8s？**
按规模选工具。我们是单机多服务的部署形态，Compose 的声明式编排完全够用，运维成本低得多。K8s 的价值在多节点调度和自愈，当前规模上它等于给自己加运维负担。**技术选型匹配规模，不追先进**。

**追问 3：有状态服务容器化要注意什么？**
数据卷必须独立挂载不能随容器销毁；备份策略单独做；升级时先备份再动数据服务。这三个是有状态容器化的基本纪律。

##### S32：钉钉与飞书开放平台集成

**一句话理解**：企业协作平台的开放能力体系，核心是三块：**身份体系**——知道谁在操作；**事件订阅**——平台上发生的事能推给你；**开放接口**——你能反向操作平台的消息、审批、日程等资源。集成的本质是把你的系统能力长进员工已经在用的工作入口。

**追问 1：事件接收有哪两种模式？怎么选？**
长连接模式和 HTTP 回调模式。长连接是客户端主动连出去，内网环境天然适配，断线自动重连；HTTP 回调要求公网可达的回调地址，要处理签名校验和加密解密。我们的环境在内网，主推长连接，但两种入口共用同一套事件处理逻辑，随时可切换。

**追问 2：安全性怎么保证？**
回调消息要做签名校验和加密解密，防伪造防窃听；事件里的用户身份要和本地账号体系做映射，映射找不到时有兜底策略；所有平台发起的操作在服务端重新做权限校验——**平台传过来的身份只作参考，权限判断永远在自己这边做**。

**追问 3：两个平台的集成经验可以迁移吗？**
可以，抽象层是相同的：事件接入、身份映射、消息发送、审批流对接这四件事，换个平台换的是接口格式不是架构。我们两个项目分别做了钉钉和飞书，第二次的集成速度明显快，因为模式已经沉淀下来了。

##### S33：消息卡片交互

**一句话理解**：把"通知加操作"压缩进一张可交互卡片——用户不用跳转系统，在消息里点按钮就完成操作。它的价值是**把操作路径从多步压缩成一次点击**，对一线移动场景尤其关键。

**追问 1：你们怎么用的？**
派工场景：主管派工后，维修员收到工单卡片，上面是接单、到场、检查、维修四个操作按钮，点对应按钮工单状态走一步，主管同步收到进度通知。维修员全程不回电脑前，操作闭环在聊天窗口里。

**追问 2：卡片回调怎么保证安全？**
回调带唯一追踪标识定位到具体工单，带点击人身份做权限校验——**不是点了就能流转**，状态机校验当前状态允不允许这个转移、这个人有没有权限，不合法直接拒绝并提示。权限永远在服务端。

**追问 3：踩过什么坑？**
回声问题：按钮触发的状态流转如果反过来又去刷新这张卡片，回调和刷新会形成循环。解法是标记来源——来自卡片回调的流转跳过卡片刷新。这类"双向触发的环"是交互集成的常见坑，要有意识地查。

##### S34：OA 审批同步

**一句话理解**：把审批平台上的流程结果自动同步进业务系统，消灭"审批过了但系统没更新"的人工搬运。设计模式是**事件驱动保实时、定时对账保正确**，两条腿走路。

**追问 1：链路怎么走？**
审批通过事件进来后，解析表单字段、落库申请记录、触发业务联动——我们的场景是写入排班表：请假时段标记请假，安排了顶岗人的连顶班一起写，还要检查顶班人和未完成工单的时间冲突，冲突就整体回滚提示。联动操作在事务里，不产生半同步的脏状态。

**追问 2：回调丢了怎么办？**
两层兜底：**定时对账任务**每天拉取最近若干天的审批单补漏，缺的补上、重复的靠幂等键挡掉；另有手动触发入口应对极端情况。事件驱动负责实时性，定时对账负责正确性——任何依赖外部推送的同步都不能只信推送。

**追问 3：幂等怎么做？**
每条审批单有平台的唯一标识，落库前先查这个标识是否处理过，处理过直接跳过。所有"可能重复到达"的事件入口都必须有幂等键，这是事件同步的第一原则。

##### S35：流式响应

**一句话理解**：服务端把响应边生成边推送给客户端，而不是攒完一次性返回。对大模型应用，它把用户感知的等待时间从"等完整回答"压缩到"马上看到内容开始动"，**是体验层面的必选项**。

**追问 1：WebSocket 和 SSE 怎么理解？**
WebSocket 是双向全双工长连接，客户端服务端可以互相随时推送，适合聊天室、实时协作这类双向场景。SSE 是基于 HTTP 的单向推送，服务端向客户端流式输出，断线自动重连，走标准 HTTP 所以网关代理天然兼容。**场景是单向输出就用 SSE，双向交互才上 WebSocket**。

**追问 2：你们项目的流式是怎么落地的？**
两处：回答生成用服务端推送流式输出，事件流里带类型标记，前端按类型分别渲染思考过程、引用来源、正文内容，用户先看到系统在想什么，再看答案逐段出来；开放平台侧用长连接通道接收事件，保证消息不丢。

**追问 3：流式输出的工程难点？**
两个：一是错误处理——流到一半失败不能给半截错误内容，要有收口机制；二是背压——生成速度超过发送速度要有缓冲策略。另外中间的反向代理要配置成不缓冲流式响应，这个配置漏了的话前端会感觉"流式失效"，是我们部署时专门检查过的一项。

#### 三、技能问答的通用应答框架（万能结构）

被问任何技能的理解时，按这个顺序组织：

1. **一句话定位**：它是干什么的、解决什么问题（十五秒）
2. **核心原理**：区别于其他方案的关键机制（三十秒）
3. **项目落地**：我们怎么用的、用在哪个环节（三十秒）
4. **取舍判断**：什么场景该用、什么场景不该用（十五秒，这是拉开差距的部分）
5. **诚实边界**：没做过的主动说"评估过没做，原因是……"加演进方向（按需）

**记住**：面试官考的不是百科全书式的知识覆盖，是**每个技能背后有没有真实的工程判断**。有判断的一分钟胜过背书式的五分钟。
