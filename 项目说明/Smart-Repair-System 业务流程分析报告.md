# Smart-Repair-System 业务域切割与交付规划

> 用途：项目启动会汇报材料。基于系统现状（21 个 API 前缀、17 个模块、3 条核心链路）从"团队刚接手、全部功能均为客户需求"的视角做系统性切割，划分逻辑可直接用于排期与分工。

---

## 汇报开场

> 这个系统表面庞大（21 个 API 前缀、17 个模块、3 条核心链路），但它的价值主线只有一条——**"工单数据 → 经验沉淀 → 智能问答 → 反哺维修"的数据飞轮**。我们的切割逻辑是：一切围绕这条主线分层，主线上的为 P0 必保，主线外围的按"替代成本 × 外部依赖"排序迭代交付。团队三人按"沉淀侧 / 消费侧 / 外部通道"分工，交叉点收敛为三个接口契约。

---

## 1. 业务域划分（7 个域）

| # | 业务域 | 核心职责 | 边界（不做什么） | 关键文件 |
|---|---|---|---|---|
| D1 | **组织与权限域** | 用户/角色/JWT 认证、排班、请假、站内通知 | 不碰工单状态；只提供"人是谁、是否可用、怎么触达" | `api/auth.py`、`api/users.py`、`api/duty_schedules.py`、`api/leave_requests.py`、`api/notifications.py` |
| D2 | **工单域**（主干） | 14 态状态机、AI 结构化分析、派工、归档校验、进度看板、历史工单导入 | 只产生"知识素材/扣库存/补故障码"请求，不自己落库；不实现检索 | `api/work_orders.py`、`agents/ticket_agent.py`、`api/dispatch.py`、`agents/work_order_importer.py` |
| D3 | **基础数据域** | 设备台账、备件库存（含 Redis 缓存）、手册错误码、故障码映射 | 纯主数据管理，不参与任何业务决策 | `api/devices.py`、`api/spare_parts.py`、`api/manual_codes.py`、`api/fault_codes.py` |
| D4 | **知识域** | 知识条目生命周期（DRAFT→UNDER_REVIEW→PUBLISHED/DEPRECATED）、抽取、三层去重、审核流、Milvus 同步 | 只读策略（403 禁止改删）；只接受"工单来源+人工审核"两种进入方式 | `api/knowledge.py`、`agents/knowledge_extractor.py`、`agents/dedup_agent.py` |
| D5 | **检索与问答域**（智能核心） | 公共检索编排（四路召回→RRF→精排→过滤→护栏）、SSE 问答、专家模式、追踪维修 | 只消费知识/手册/备件，不写任何业务数据 | `agents/retrieval_flow.py`、`agents/tools.py`、`api/search.py`、`agents/answer_generator.py`、`agents/expert_repair_agent.py`、`agents/guided_repair_agent.py` |
| D6 | **钉钉集成域**（外部通道） | 扫码/H5 免登、通讯录同步、Stream+HTTP 双回调、机器人三层意图路由、互动卡片、OA 审批同步、消息推送 | 一切内部动作委托其他域：建单→D2、查单→D2、检索→D5、排班写回→D1 | `api/dingtalk.py`、`core/dingtalk_stream.py`、`core/dingtalk_oa_sync.py`、`core/dingtalk_wo_card.py`、`agents/robot_graph.py` |
| D7 | **支撑与基础设施域** | 推理服务（Qwen3-Embedding-4B + Qwen3-Reranker）、MCP 服务、数据驾驶舱、PG/Milvus/Redis 数据底座 | 横切能力，不承载业务规则 | `core/embeddings.py`、`core/reranker.py`、`mcp/server.py`、`api/dashboard.py` |

**划分依据**：职责边界 = "谁能改数据、数据给谁用"。D2/D4/D5 是飞轮三段（产生→沉淀→消费），D3 是三者共用的主数据，D1 是人的维度，D6 是所有能力的移动端投影，D7 是地基。

## 2. 需求优先级分层

| 层级 | 包含功能 | 划分依据 |
|---|---|---|
| **P0 · MVP（闭环必需，先交付）** | 用户登录+三角色权限、设备台账、工单状态机核心（创建→流转→完成→归档）、AI 结构化分析、知识抽取+去重+审核+同步、Web 智能问答（基础版）、推理服务、数据底座 | **离开它飞轮断裂**：工单完成不能沉淀、沉淀不能检索，业务价值不成立 |
| **P1 · 管理闭环（第二期）** | 派工+排班/请假冲突预检、备件库存扣减与查询、故障码映射自动补全、站内通知、进度看板、历史工单 PDF 导入 | 没有它工单仍可跑，但**管理不可控**；属于"把闭环做完整"，不做闭环才不成立 |
| **P2 · 生态与增值（迭代交付）** | 钉钉全家桶（登录/机器人/卡片/OA）、专家模式、追踪维修、MCP、数据驾驶舱 | ① **有替代通道**（Web 可完成全部管理操作）② **外部依赖风险**（钉钉平台 API 变动/审批流配置）③ **纯增量**（驾驶舱/MCP 不改变业务能否运转） |

**四条分层依据**：**① 价值闭环**（断链即 P0）→ **② 替代通道**（有低成本替代即可后置）→ **③ 外部依赖**（依赖第三方平台的功能风险高，靠后并隔离）→ **④ 复用性**（`retrieval_flow` 公共编排层、权限中间件被四端复用，必须先行沉淀）。

## 3. 模块依赖关系梳理

### 3.1 三层结构

```
┌─ 对外接口层 ──────────────────────────────────────────────┐
│ FastAPI 21 路由 + SSE 流式 + 钉钉 Stream/HTTP 回调 + MCP   │
├─ 业务逻辑层 ──────────────────────────────────────────────┤
│ ticket_agent / knowledge_extractor / dedup_agent /        │
│ retrieval_flow(公共编排) / expert_repair_agent /           │
│ guided_repair_agent / robot_graph / work_order_importer    │
├─ 基础设施层 ──────────────────────────────────────────────┤
│ PostgreSQL 16（业务事实库）│ Milvus 2.4（双集合）│ Redis 7  │
│ 推理服务 Qwen3-Embed-4B + Qwen3-Reranker（独立进程 8010） │
└───────────────────────────────────────────────────────────┘
```

### 3.2 域间依赖与数据流

| 域 | 依赖 | 被依赖 | 关键数据流 |
|---|---|---|---|
| D1 组织权限 | 钉钉（通讯录来源） | D2（派工预检）、D6 | 钉钉通讯录→users；OA 审批→leave/duty→派工冲突预检 |
| D2 工单 | D1（权限/预检）、D3（设备/备件/码）、D4（抽取发布）、D6（卡片回调） | D5（问工单）、D6（机器人查单）、D7（驾驶舱数据源） | 完成时四连击：AI 分析→抽知识→扣库存→补故障码 |
| D3 基础数据 | D7（推理服务？否，纯 CRUD） | D2、D4、D5 | 备件→Redis 缓存→问答库存查询 |
| D4 知识 | D2（工单来源）、D7（Milvus 同步） | D5（检索依据） | PUBLISHED→同步 Milvus→检索命中→反哺新工单（**飞轮**） |
| D5 检索问答 | D3（备件查询）、D4（知识/Milvus）、D7（推理服务） | D6（机器人问答）、对外四端 | 四端（Web/专家/钉钉/MCP）共用 `retrieval_flow`，杜绝策略漂移 |
| D6 钉钉 | D1/D2/D5 全部 | 无（纯出口） | 只做"外部消息↔内部动作"翻译 |
| D7 支撑 | 无 | 全部 | 推理服务故障→降级矩阵（BM25-only/规则重排），"降级不降可用性" |

**三个关键契约**（团队交接的接口边界）：**① 知识条目结构**（工单→抽取→Milvus 的字段契约，D2/D4/D5 交汇点）；**② 工单完成事件**（触发抽取/扣库存/补码，D2 对 D4/D3 的输出契约）；**③ OA 审批同步**（钉钉→排班落库+冲突回滚，D6→D1 的写契约）。

## 4. 团队分工建议

### 4.1 三人方案（推荐）

| 成员 | 负责域 | 理由 |
|---|---|---|
| **A · 业务主干** | D2 工单域 + D4 知识域 | 状态机/抽取/去重是**业务规则最重**、领域知识最密集的部分，一人独掌保证规则一致性；同时握有飞轮"产生→沉淀"两段，闭环叙事完整 |
| **B · 算法与底座** | D5 检索问答 + D3 基础数据 + D7 支撑 | 检索精度/降级矩阵/阈值标定是**算法密集型**工作，与模型服务天然同组；D3 为检索提供过滤依据，内聚度高 |
| **C · 集成与体验** | D6 钉钉 + D1 组织权限 + 前端 + 驾驶舱 | 钉钉是**外部平台集成**（SDK/回调/加密签名），技能栈独立；前端与驾驶舱归 C 使 Web 体验端到端可控 |

**交叉点收敛**：A↔B 契约=知识条目结构+Milvus 数据结构；A↔C 契约=OA 排班同步+派工通知事件；B↔C 契约=机器人复用 `retrieval_flow`、卡片回调走工单 transition。三对契约全部是**接口级**，无代码级耦合。

### 4.2 两人方案（备选）

| 成员 | 负责域 | 理由 |
|---|---|---|
| **A · 沉淀侧** | D1 + D2 + D3 + D4 | 保证"知识进得来"：组织、工单、主数据、知识全归 A，飞轮上游一条线 |
| **B · 消费侧** | D5 + D6 + D7 + 前端 | 保证"知识用得上"：检索、钉钉、支撑、界面全归 B，一切"往外输出"的能力一条线 |

双方唯一契约 = **Milvus 知识条目结构 + 工单完成事件**，一个文件级协议即可解耦。代价：A 负担重（工单域最大），排期需向 M2-M3 倾斜。

## 5. 交付里程碑规划

| 里程碑 | 周期 | 交付内容 | 验收标准 | 并行项 |
|---|---|---|---|---|
| **M1 地基** | W1-2 | 数据底座（PG/Milvus/Redis）、推理服务、D1 用户权限最小集、D3 设备/备件 CRUD | 可登录、可建设备备件、`/health` 三绿 | — |
| **M2 工单主干** | W3-5 | D2 状态机核心 + AI 分析 + 归档 | 工单全生命周期可走通（知识未接） | C 启动钉钉开发者账号申请/环境预研（无代码） |
| **M3 飞轮闭环** ★MVP | W6-8 | D4 抽取/去重/审核/同步 + D5 四路检索 + SSE 基础问答 | **工单完成→自动沉淀→新问题可检索回答**，飞轮首次转通 | — |
| **M4 管理闭环** | W9-11 | D2 派工+预检、D3 库存扣减、D1 排班/请假/通知、故障码补全、看板、PDF 导入 | 主管端到端可管控：派工有预检、完成扣库存、看板实时 | 专家模式/追踪维修（依赖 D5，可先行原型） |
| **M5 移动与深度** | W12-14 | D6 钉钉全家桶 + 专家模式 + 追踪维修 | 移动端可报修/查单/卡片流转；复合故障可拆解分组回答 | 驾驶舱开发（依赖 M4 数据） |
| **M6 生态与打磨** | W15-16 | 驾驶舱、MCP、阈值标定、压测、文档 | 可交付验收 | — |

**排序逻辑**：严格按依赖链推进（底座→主干→沉淀→消费→管理→生态），**M3 是价值验证点**——提前了功能不完整、延后了价值不成立；P2 项全部具备"可并行启动"条件，但验收必须卡在依赖方完成后，避免半成品等待。

## 一页纸主线（汇报收尾）

> 七个域、三张契约、两个里程碑（M3 飞轮转通、M5 移动可用）——主干三个人拧成一股绳，外围每个人可以独立跑。
