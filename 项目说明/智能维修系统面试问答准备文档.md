### 模块零：项目整体与背景

#### Q1：用 30 秒介绍一下这个项目

**答**：这是一个面向制造企业的智能维修知识平台。核心痛点是：工厂里设备故障的排查经验都在老师傅脑子里，靠口口相传，新人遇到问题要么到处问人、要么翻厚厚的纸质手册，历史修过的工单也基本没人回头看。

我们做的事情可以概括成一句话：**让每一次维修都自动变成下一次维修的答案**。系统把工单的全生命周期管起来，工单完成时 AI 自动把故障原因和处理方案抽取成知识条目，审核入库并同步到向量库；维修人员用自然语言提问，系统通过混合检索命中历史案例和设备手册，直接给出诊断建议。形成"维修→沉淀→问答→反哺维修"的数据飞轮。

我全程参与这个项目，是第二负责人，主要负责多智能体编排、检索链路和钉钉集成这几块。

#### Q2：这个系统谁在用？解决什么问题？

**答**：三类角色。**维修员**是最高频用户，在钉钉里直接问机器人"注塑机合模报警怎么处理"，几秒就能拿到历史案例的处理方案；也可以通过互动卡片接单、汇报进度，不用回电脑前操作。**主管**负责派工、审核知识、看数据看板。**管理员**维护设备、备件、故障码这些基础数据。

解决的问题分三层：第一层是**经验复用**，把老师傅的隐性经验变成可检索的显性知识；第二层是**流程数字化**，工单从派工到归档全程留痕，排班、备件消耗自动联动；第三层是**决策辅助**，什么设备老坏、哪个维修员负载高，看板一目了然。

#### Q3：你在项目中的职责是什么？

**答**：我是项目的第二负责人，全程参与。分工上我主要承担三块：一是**多智能体架构**，包括问答图和钉钉机器人图的编排设计、意图路由和专家模式的实现；二是**检索链路**，四路召回、融合、精排和降级兜底这条主线是我参与落地的；三是**钉钉集成**，机器人问答、互动卡片和 OA 审批同步。同时参与了知识沉淀闭环的设计和联调。项目是多人协作的，架构决策是我们一起讨论定的，我负责其中核心模块的实现。

#### Q4：整体技术架构是怎样的？

**答**：四层结构。**对外接口层**有三个入口：Web 管理端、钉钉机器人，还有 MCP 工具接口，三端复用同一套检索能力。**业务逻辑层**是核心，多智能体编排在最上面，下面是工单、知识、设备、备件这些领域模块。**智能服务层**是独立部署的推理服务，承载 Embedding 编码和 Reranker 精排，对外提供 OpenAI 兼容接口。**基础设施层**是 PostgreSQL 存业务数据和做关键词检索、Milvus 存向量、Redis 做缓存，整套用 Docker Compose 编排。

大模型推理走私有化部署，数据不出内网，这是制造企业的硬要求。

#### Q5：这个项目最难的地方是什么？

**答**：我认为最难的有两点。

第一是**检索质量的冷启动和持续优化**。知识库刚开始只有手工录入的设备手册，维修员的提问又特别口语化，还有中英文混杂的设备日志，一开始检索命中率很低。我们的解法不是一上来就调参数，而是先建了一套回归验证的方法：从真实工单里挑典型问题构造验证集，逐条跑检索链路人工评估，定位出五个具体问题——比如英文日志完全检不到、故障码被当成普通词处理——逐个修复后再回归。这个"建验证集→定位→修复→回归"的过程比最终的数字更有价值。

第二是**多角色多端的一致性**。同一套业务逻辑要在 Web、钉钉、MCP 三个入口表现一致，还要处理回调丢失、并发操作这些分布式场景的边界情况，这块我们靠状态机白名单加幂等设计来保证。

### 模块一：多智能体架构与编排

#### Q6：为什么选 LangGraph 而不是 LangChain Agent 或者直接写 if-else？

**答**：我们的场景特点是**流程多分支、且大量节点不需要 LLM**。比如意图路由，8 种意图里有一大半可以用规则直接命中；工单处理是固定的三步流水线。这种场景用 LangChain 的 ReAct Agent 有两个问题：一是每一步都要过 LLM，成本高、延迟高；二是流程不可控，Agent 自己决定下一步走哪，出问题了很难定位。

纯 if-else 能解决可控性，但分支一多就成了意大利面条，加一个新意图要动路由函数本身，改动面大。

LangGraph 的状态图模型刚好在中间：节点是明确的函数，边是显式的条件路由，**流程可视化、可测试、可断点**。我参与设计的一个关键原则是"能走规则不走模型"，图里的条件边大量是零成本的规则判断，只有真正需要语义理解的节点才调 LLM。而且图可以嵌套，主图里可以挂子图，复用性很好。

#### Q7：你们设计了哪些状态图？各自干什么？

**答**：三张图，按业务域划分。

第一张是**问答图**，服务 Web 端和 MCP 端，负责查询清洗、意图判断、混合检索、精排过滤、生成回答这条主线，多故障复合问题还会走专家模式的拆解分支。

第二张是**钉钉机器人图**，接收钉钉消息后先做三层意图路由，分发到不同分支：问知识库的走检索问答，查工单的走工单查询子图，问库存、排班的走对应工具节点，识别不了的走兜底。它复用问答图的检索能力，不重复造轮子。

第三张是**工单导入图**，处理历史 PDF 工单的批量导入：解析文本、OCR 识别、结构化抽取、去重检查，每一步都有独立节点，哪步失败不影响其他文件。

这样划分的好处是**每张图的职责单一，图之间通过共享的检索层和领域服务通信**，加新入口只需要加图，不用动核心逻辑。

#### Q8：意图路由是怎么做的？什么时候调大模型？

**答**：三层漏斗设计，核心思想是**把高频简单意图拦在模型前面**。

第一层是零成本的快速通道：工单号有固定的编号格式，用正则就能识别；纯数字、纯设备名、带"库存""备件"这类关键词的，直接查表命中。日常消息里这一层能拦下大部分，完全不消耗模型调用。

第二层才调大模型做语义分类，覆盖 8 种意图，温度设成 0 保证稳定。

第三层是规则兜底：如果模型调用失败或者超时，退回到关键词规则，保证系统永远有响应。

另外有个细节：机器人场景用户可能发任意闲聊，我们在进检索之前还加了意图阀门——先用低成本方式判断这条消息是不是真的在问维修问题，不是的话直接走闲聊回复，**避免把"你好"这种消息也丢进检索链路浪费资源**。

#### Q9：专家模式是怎么拆解复合故障的？为什么需要它？

**答**：先说为什么需要。复合问题比如"注塑机合模报警，而且油温还偏高"，如果当成一句话去检索，两个故障的语义会互相稀释，召回的案例可能哪个都不贴切。

方案本质上采用 **Plan-and-Solve 策略**：先把复合问题**规划拆解成多个单故障子任务，再并行检索求解、按故障分组回答**。拆解分两步：先用规则预检，有"而且""还有"这类连接词并且包含多个故障信号词的才进入拆解，否则直通单路检索，不浪费一次模型调用；预检命中后由大模型做结构化拆解，为了保证可控，子查询数量设了上限。

执行层面几个关键设计：子查询**并行检索**，整体设超时保护，单个子查询失败只影响它自己那组，不拖垮整个回答；每个故障小节的回答只引用自己的检索结果，**从源头避免串味**；回答按故障分组流式输出，前端可以逐组渲染。

**追问：这算 Plan-and-Solve 吗？和带反思的完整版有什么区别？**
算，我们是它的**静态版落地**：一次性规划拆解、并行求解，执行中不修改计划。选静态版是判断过场景的——故障拆解的结构相对固定，一次拆对的概率高，静态计划延迟低、成本省；而且我们在子任务级别做了补偿，单个子查询质量差会单独触发深度检索救援，不推翻整个计划。如果场景里计划经常中途失效，就该升级成带反思重规划的完整版——我在飞书助手项目里就实现了那个形态，规划、执行、反思、综合四阶段，反思不通过最多重规划三轮。**两种形态的取舍标准就是：计划会不会中途失效。**

#### Q10：什么时候触发 ReAct 救援？为什么是管道优先？

**答**：管道优先是成本考虑。标准检索管道是固定流水线：召回、融合、精排、过滤，一次调用就出结果，快且便宜。ReAct 是让模型自己决定"检索效果不够就换个方式再查"，灵活但每一轮都要过模型，还容易打转，我们设了最大迭代轮数防止死循环。

所以策略是：**每个子查询先走管道，用规则对检索结果做质量评估**——注意这个质检也是规则不是模型，比如结果条数够不够、高分结果有几条。达标就直接用，不达标才升级到 ReAct 深度检索，让模型自主决定换检索方式、改写查询词再试。

实际跑下来大部分查询管道就能达标，只有少数特别刁钻的才走深度检索。这样把昂贵的模型推理只留给真正需要的查询，整体延迟和成本都可控。

#### Q11：并行检索某个子查询失败或者超时怎么办？

**答**：三个层次的防护。第一，**整体超时保护**，所有并行任务加起来超过设定时间就强制收口，用已经拿到的结果回答，不让用户干等。第二，**任务级隔离**，单个子查询抛异常只影响它自己那组，其他故障的回答正常输出，失败的组会明确告诉用户"这个故障暂时没查到"。第三，**检索本身有降级**，向量服务挂了自动切纯关键词检索，结果可能差一点但功能不中断。

设计原则就是：专家模式是锦上添花的深度能力，**它的任何故障都不应该让基础问答不可用**。

#### Q12：你们是怎么控制大模型调用成本的？

**答**：贯穿整个系统的原则是"能规则解决的不调模型，能小模型解决的不调大模型"。具体几个点：意图路由的快速通道和规则兜底零模型成本；复合故障的规则预检先拦一道；检索结果的质检用规则不用模型；去重环节只有相似度达到一定阈值的候选才让模型做实质判断，绝大部分用规则和向量距离就筛掉了；错误码识别用正则不用模型，识别结果还带缓存。

另外会话上下文做了压缩，长对话只保留最近的增量加摘要，不会把整个历史塞进每次请求。这些加起来，日常高频请求里真正走大模型的比例被压得很低。

### 模块二：RAG 检索链路

#### Q13：把检索链路整体讲一遍

**答**：整条链路五个阶段：**多路召回 → 融合排序 → 严格过滤 → 精排 → 回答护栏**。

用户提问进来，先做查询清洗，去掉无关的语气词、提取错误码和关键实体。然后并行发起多路召回：向量检索管语义近似，关键词检索管字面精确，如果识别出了设备错误码，还会额外走手册的错误码精确匹配和日志码语义匹配。多路结果用 RRF 按名次融合，解决各路分数不可比的问题。融合后做严格过滤，设备对不上、故障类型对不上的直接剔掉，防止串味。留下的头部候选交给 Reranker 做交叉编码精排。最后回答层还有一道护栏，没有可信案例时直接回复"未检索到"，**绝不让模型硬编**。

每一环都有降级方案，后面逐一说。

#### Q14：为什么要向量加 BM25 混合，单用一路不行吗？

**答**：两路的盲区刚好互补。

向量检索强在语义近似：用户说"电机嗡嗡响"，知识库里写的是"马达异响"，字面不同但向量距离近，能召回。但它的弱点是**专有标识符**——设备错误码、型号这种没有语义的字符串，向量化之后区分度很差。

关键词检索反过来：错误码、型号、品牌名这种精确字面匹配是它的强项，但遇到口语化表达就没辙了，"机器不动了"和"设备停机"关键词重合度很低。

我们的查询恰恰两类都有：维修员口语描述故障现象是一类，直接报错误码查手册是另一类。所以必须双路。实测里很多查询是**一路漏掉另一路捞回来**的，单路召回的漏检在混合后基本被补上了。

#### Q15：你们到底几路召回？什么情况两路什么情况四路？

**答**：基础是两路：知识库的向量召回加知识库的关键词召回，任何查询都走。

当查询里识别出设备错误码时，动态扩展成四路：加一路**手册错误码精确匹配**，错误码在手册错误码表里做精确等值查询，命中直接给最高权重——这是确定性路径，不存在语义误差；再加一路**手册日志码语义匹配**，针对设备日志里的英文代码。

错误码识别本身用正则，零模型成本，识别出的码表还带短时效缓存避免重复解析。这个动态切换的设计逻辑是：**确定性信号出现了就用确定性路径，没有就退回语义路径**，不做无谓的多路开销。

#### Q16：多路结果怎么融合？为什么用 RRF 而不是加权分数平均？

**答**：核心问题是**各路的分数不可比**。向量检索的余弦相似度在 0 到 1 之间，关键词检索的 BM25 分数理论上无上界，两个分数直接加权平均没有意义，加权系数也没法调——同一组权重在这个查询上合理，换个查询就失衡了。

RRF 的巧妙之处在于**只看名次不看分数**：每条结果在每一路里排第几名，贡献一个"1 除以常数加名次"的分数，各路相加。这样不管各路分数量纲如何，融合结果都稳定。常数我们取 60，这是原始论文的经验值，作用是抑制头部名次的差距——第 1 名和第 2 名的差距不应该比第 10 名和第 11 名大太多。

还有一个隐性好处：**双路都命中的结果天然排最前**。一条案例既被语义召回又被关键词命中，说明两种证据都指向它，可信度当然更高。这个"交叉验证"效果是加权平均做不到的。

#### Q17：跨库融合时 ID 冲突怎么解决？

**答**：这是我们踩过的真实坑。知识库条目和手册条目是两个库，主键都是自增整数，融合去重的时候发现**知识库的 id 为 5 和手册的 id 为 5 被当成了同一条**，互相覆盖。

解法是给每条结果构造**复合去重键**：手册类的条目加类型前缀，跨库永远不会撞；同一个知识条目可能通过向量路和关键词路两次被召回，用它的业务主键归并，保证同一条只算一次分数但多路命中会累加 RRF 贡献。去重键的优先级是：业务键存在用业务键，其次用带前缀的复合键。

这个问题不大但不解决会出隐性错误——检索结果莫名少一条、分数算错，而且很难排查。我们后来把这类"跨数据源标识冲突"当成融合层的标准检查项。

#### Q18：融合后的严格过滤是过滤什么？会不会误杀？

**答**：过滤两个维度：**设备维度**和**故障维度**。查询里如果明确提到了设备，候选案例的设备对不上就剔掉；故障类型关键词对不上也剔掉。

为什么要这么严？因为维修场景的"串味"代价很高——把 A 设备的处理方案推荐给 B 设备的故障，轻则没用，重则误导操作。宁可少给，不能给错。

误杀的防护有两层：第一，过滤只在查询确实带了明确的设备或故障信号时才生效，模糊查询不过滤；第二，**严格过滤之后如果结果为空，会触发语义兜底**——放宽到纯语义相似度，用一个更高的阈值捞回最相关的几条，并明确告诉用户这是放宽条件的结果。所以链路是"先严后松"，既有原则性又有兜底。

#### Q19：为什么还要 Reranker？它和向量检索不是重复了吗？

**答**：不重复，是分工。向量检索是**双塔结构**，查询和文档各自独立编码成向量再算距离，好处是文档向量可以预先算好存起来，检索时只需要编码查询，速度快、能扛大规模库；代价是查询和文档之间没有交互，语义理解的深度有限。

Reranker 是**交叉编码**，把查询和候选拼在一起进模型，词级别的注意力交互，判断精度高得多；代价是没法预计算，每对都要现算，所以只能用在少量候选上。

这就形成了经典的两阶段架构：**向量检索负责从大库里快速圈出候选，Reranker 负责在小范围里精细排序**。我们实测下来，加了精排之后头部结果的排序质量明显改善，特别是那些向量分数接近、靠语义深浅区分的高难案例。

#### Q20：精排为什么只对头部 30 条？精排模型挂了怎么办？

**答**：30 条是效果和成本的平衡点。精排是交叉编码，每对查询-候选都要过一次模型，候选数线性增加延迟。我们测下来头部 30 条已经覆盖了绝大多数正确答案——RRF 融合后正确答案基本都在前列，再往后的候选就算精排也翻不了盘。30 条里取最终的前 10 条进入回答，压缩比合理。

工程上还有几个细节：候选分批送进模型避免一次输入过长；精排调用设超时；**精排只重排不过滤**，不会把候选删掉，过滤是上一环节的职责，职责分离。

降级方案：精排服务挂了或者连续失败，自动切换到**规则加权重排**——设备匹配的加权、命中错误码的加权、多路命中的加权，用确定性规则近似精排的判断。效果会差一点，但功能连续。服务恢复后自动切回精排，不需要人工干预。

#### Q21：0.45 这个过滤阈值是怎么定的？

**答**：数据驱动标定的，不是拍的。过程是这样：

我们拿验证集跑全链路，把检索分数的分布打出来，发现一个很清晰的现象——**无关结果和真正相关的结果之间存在一个真空带**：无关查询的最高分集中在一个较低区间，而正常故障查询的最低分明显更高，中间有一段几乎没有样本。阈值就定在真空带中间，这样两边都不误伤。

这个值是迭代出来的，前后调过两版：第一版定得太低，闲聊类查询也能混进来；后来收紧到现在这个值，又专门做了回归——正常故障查询全部放行，无关闲聊全部拦截，两头都验证过。

阈值还做了**分层**：粗筛用一个阈值把明显无关的挡掉，去重判断用另一个更高的阈值控制模型调用成本，不同环节的目标不同，阈值不共用。所有这些参数都在统一的配置里管理，标定脚本可以随时重跑。

#### Q22：英文设备日志怎么检索中文知识库？跨语言问题怎么解的？

**答**：这是我们碰到的真实难题。设备的 PLC 日志是英文的，比如报警描述是英文短语，但知识库里的维修案例全是中文。一开始英文查询基本检不到东西。

解法分三层。**第一层靠 Embedding 模型本身的多语言能力**，我们选的 Qwen3-Embedding 原生支持上百种语言，中英跨语言语义对齐是它的基本能力，英文故障描述和中文案例之间本身就有可用的向量相似度。**第二层是人工词表补强**，我们整理了一份英文故障术语到中文的映射表，高频故障词先翻译再检索，把最容易失配的部分兜住。**第三层是语义兜底阈值**，英文查询如果严格过滤后为空，用放宽的语义阈值再捞一次。

效果上，优化前英文日志查询基本不可用，优化后能够稳定检到相关案例，而且没有引入无关结果。这是我们回归验证里最典型的"从不可用到可用"的改进。

#### Q23：怎么防止模型编造答案？检索不到时怎么处理？

**答**：回答层有一道**确定性护栏，不经过模型**。逻辑很简单：检索结果为空，或者最高分低于可信阈值，就不调用大模型，直接返回固定话术"未检索到相关案例，请联系资深工程师"。

为什么不让模型自己判断要不要编？因为**把幻觉的控制权交给模型本身就是风险**，模型会"礼貌性地硬答"。我们的原则是：能不能回答这个问题，由确定性的检索结果决定，模型只负责"把检索到的内容组织成通顺的建议"，并且回答里强制附上引用的案例来源，用户可点开核对。

这个设计也回答了"大模型不可控怎么办"——**可控性不是靠提示词约束出来的，是靠链路设计保证的**：低置信场景根本走不到模型那一步。

#### Q24：查询进检索之前做了哪些预处理？为什么要做？

**答**：三类清洗。**第一类是噪声去除**，维修员在钉钉里发消息经常带语气词、表情、重复内容，这些进检索会稀释语义。**第二类是结构化提取**，用正则把错误码、设备型号这类确定性信号抽出来，错误码走精确匹配路，不进语义检索。**第三类是中英拆分**，一条消息里中文描述和英文日志码混着的时候，分别处理——中文部分走知识库检索，英文码走手册匹配。

清洗放在检索前的原因是**垃圾进垃圾出**，检索链路的每一环都在放大查询的质量，前置清洗的性价比最高。而且这些处理全是规则和轻量解析，零模型成本、毫秒级，不影响响应速度。

### 模块三：知识沉淀闭环

#### Q25：知识沉淀闭环整体讲一遍

**答**：闭环的起点是工单完成。维修员提交完成时，系统触发四件事：AI 对工单做标准化分析补全缺失字段、**自动抽取知识条目**、扣减消耗的备件库存、补全故障码映射。

抽取出来的知识条目不会直接入库，先过**三层去重**：跟已有知识比，是重复的就合并掉；不重复的进入**人工审核队列**，主管确认内容准确、脱敏干净，才点发布。发布的同时同步向量索引，**同步失败会回滚发布状态**，保证"库里有就必然检得到"。

从此这条知识就能被后面的检索命中——下一个遇到同样故障的维修员，提问就能查到前任的处理方案。这就是飞轮：工单越多知识越厚，检索越准，维修越快，沉淀质量也越高。

#### Q26：知识抽取具体抽什么？为什么不让维修员自己写总结？

**答**：抽取的内容是结构化的：**故障标题、故障现象、根因分析、处理方案、适用设备**这几个固定字段。输入是工单的完整上下文——报修描述、维修过程记录、完成情况。

为什么用 AI 抽取而不是人工写？两个原因。一是**写总结是反人性的**，维修员干完活只想赶紧关单，让他写结构化总结，要么不写要么敷衍，知识质量无法保证；二是**格式统一**才能保证后面检索和去重的一致性，AI 抽取天然输出统一结构。

当然 AI 抽取不能全信，所以后面有人工审核兜底。**AI 负责把隐性经验低成本地显性化，人负责把关准确性**，这个分工是整个闭环成立的关键。

#### Q27：三层去重链是怎么设计的？

**答**：从便宜到贵三层。

**第一层是故障码精确匹配**。两条知识的故障码一样，大概率是同一个问题，直接用确定性比对判断，零模型成本，先把最容易判的判掉。

**第二层是向量相似度筛候选**。新知识向量化后去库里召回相似条目，相似度低的直接放行，只有超过候选阈值、疑似重复的才进入下一层。

**第三层是模型实质判断**。把疑似重复的两条交给大模型，让它对比故障原因和处理方案，判断是不是实质重复。这里有个关键的阈值分层：向量阈值只管"要不要叫模型来看"，调不调模型是成本问题；模型判断结果才是"到底重不重复"，是准确性问题。

整个链的设计原则是**保守不判重**——任何一层不确定，就放行进审核队列，宁可让人多审一条，不可误杀一条有价值的知识。因为误删不可逆，多审只是成本。

#### Q28：为什么相似度高不能直接判定重复？

**答**：这是我们最早踩的坑。一开始想过直接用相似度阈值判重，但很快发现不成立：**同一台设备、同一个故障码，完全可能有两套不同的处理方案**。比如同一个报警码，可能是传感器问题，也可能是线路问题，两条知识标题几乎一样、向量相似度极高，但处理方案完全不同——这恰恰是最有价值的知识，因为维修员需要根据实际情况二选一。

反过来，两条相似度一般的知识，也可能在说同一件事，只是表述习惯不同。

所以相似度只能回答"像不像"，回答不了"是不是同一个知识点"。**"是不是"要看内容实质——故障原因是否相同、处理方案是否可互换**，这个判断需要语义推理，只有模型能做。这也是为什么去重链里模型是不可省略的最后一环。

#### Q29：为什么还要人工审核？AI 判完不就够了吗？

**答**：三个原因。

第一，**错误的代价不对称**。知识条目是后面所有回答的依据，一条错误知识入库，会影响之后每一次检索到它的问答，错误被放大的；而审核一条知识只要几十秒。用几十秒的人工换掉一个持续性的错误源，非常划算。

第二，**脱敏和合规**。工单里可能有客户信息、敏感的设备参数，AI 抽取做了基础脱敏，但合规责任必须有人承担。

第三，**审核本身是质量数据的来源**。审核通过率、驳回原因，这些反馈能告诉我们抽取环节哪里做得不好，是持续优化的输入。

另外知识库做了**只读设计**：知识条目不能直接改、直接删，只能通过工单沉淀加审核进入。有人问这不是不灵活吗？是的，但检索系统最怕的就是依据被随意改动，今天改一条明天删一条，回答质量无法归因。只读保证了**每一条进库的知识都有来源、有审核人、有版本**。

#### Q30：历史 PDF 工单是怎么批量导入的？

**答**：冷启动必须解决的问题——上线前积累了大量纸质扫描的工单，这是存量知识的来源。

我们做了一条导入流水线，本质也是一张状态图：上传 PDF、文本解析、**识别不了的走 OCR 兜底**、结构化抽取成知识条目、逐条过三层去重、最后进人工确认队列。

几个关键设计：文件级隔离，一个 PDF 解析失败不影响其他文件；解析质量参差不齐，所以**导入的条目一律进待确认状态，不直接发布**，人工确认后才生效——存量数据质量没保障，就不能让它直接污染检索；去重逻辑和实时沉淀复用同一套，不分叉。

这条流水线把几年的存量工单变成了知识库的初始底座，飞轮不是从零转起来的。

#### Q31：数据飞轮如果转不起来，你们怎么冷启动？

**答**：冷启动分三步。**第一步是手册打底**，设备厂商的维修手册先结构化入库，这保证了哪怕一条工单知识都没有，错误码查询也能用。**第二步是存量导入**，刚说的 PDF 流水线把历史工单变成初始知识。**第三步是激励沉淀**，上线后每个新完成的工单都自动抽取，审核员定期清理队列，让入库速度跟上产生速度。

飞轮的启动点是第二步——存量知识进去之后，第一批用户提问就能得到有用的回答，信任建立了，维修员才愿意好好填工单，新知识的产生速度才起得来。

#### Q32：抽取的知识质量不行怎么办？

**答**：质量防线是前置的，不是事后补救。抽取的输入有要求：工单的关键字段为空就不触发抽取，**垃圾进不如不进**。抽取的提示词强制结构化输出，每个字段有明确的填写要求。审核环节驳回的条目会积累成样本，定期分析驳回原因的分布，哪类字段错得多就针对性调抽取策略。

另外发布后的知识也不是永久有效的，设备换代、工艺变更后知识会过期，所以知识库支持**下架**操作——不是删除，是标记失效，退出检索但保留记录。这比物理删除安全，可追溯。

### 模块四：钉钉集成

#### Q33：为什么要接钉钉？整体怎么设计的？

**答**：制造企业的一线维修员不在电脑前，他们在车间，手机上的钉钉是他们的工作入口。**让 AI 能力长在维修员已经在用的工具里**，而不是让他多装一个 App，这是推广的前提。

我们在钉钉上提供三类能力：**机器人问答**，单聊里直接问故障怎么处理；**互动卡片**，派工通知、进度确认都是卡片按钮，点一下就驱动工单状态流转；**OA 审批同步**，钉钉上提请假审批，通过后自动写入系统排班表。

技术上走钉钉的长连接模式接收事件，机器人消息、审批事件、卡片回调三类事件统一进事件处理层，再分发到对应业务模块。

#### Q34：为什么用长连接模式而不是 HTTP 回调？

**答**：两种都支持，生产环境主推长连接，原因是**部署约束**。

HTTP 回调要求服务有公网可达的回调地址，要处理签名校验、加密解密，而且回调是钉钉主动打过来的，网络抖动、服务重启期间的消息会丢。我们的部署环境在内网，没有固定公网入口，长连接模式是客户端主动连出去，**内网环境天然适配**，断线了 SDK 自动重连，消息由钉钉侧保持投递。

但我们没有把路走死：HTTP 回调通道也实现了，和长连接**共用同一套事件处理逻辑**，入口不同、处理同一。这样客户环境如果有公网条件也能切过去，而且定时兜底任务不依赖任何一种模式，两条路都断了数据还能补。

#### Q35：为什么用互动卡片？按钮怎么驱动状态机？

**答**：先说为什么。派工之后维修员要接单、到场、开始检查、开始维修，如果每个动作都要打开网页点，没人会用。**卡片把操作压缩成一次点击**：主管派工后，维修员的钉钉里弹出一张工单卡片，上面四个按钮，点对应按钮工单状态就走一步，同时主管那边收到进度通知。

实现上几个细节：每张卡片有唯一的外部追踪 ID，回调时靠它找到对应工单；按钮回调里带点击人身份，**权限校验在服务端做**——不是点了就能流转，状态机校验当前状态允不允许这个转移、这个人有没有权限，不合法直接拒绝并提示。

还有个防回声的设计：卡片按钮触发的状态流转，不会再反过来去刷新这张卡片，否则回调和刷新会形成循环。

#### Q36：14 态状态机是怎么设计的？为什么这么多状态？

**答**：状态多是业务驱动的，不是为了复杂。维修现场的真实流程就是：派工之后维修员要**接单确认**、**到场打卡**、**开始检查**、**开始维修**，每一步主管都想知道进度，所以每个环节是一个独立状态。再加上草稿、提交、完成、归档这些单据状态，以及退回等分支状态，一共 14 个。

设计的核心不是状态本身，是**转移白名单**：每个状态只能去规定好的下几个状态，任何非法转移直接拒绝。这带来两个好处：一是**任何时刻工单处于什么状态、下一步能去哪，都是确定的**，并发点击、重复回调都不会把单子搞乱；二是权限可以按转移来配，比如"归档"这个动作只有主管能做，就是在转移上加角色校验。

每次状态转移都写一条进度日志，谁在什么时候把单子从哪推到哪，全程可审计。

#### Q37：OA 审批同步是怎么做的？回调丢了怎么办？

**答**：场景是维修员在钉钉提请假审批，主管批了之后，我们的系统要知道这件事，并且自动改排班——请假时段的班次要标记为请假，如果安排了顶岗人，顶岗人的班次也要写进去，还要检查有没有冲突的未完成工单。

链路上，审批事件通过事件通道进来，解析表单字段、落库请假单、通过后应用排班变更。**排班变更和工单冲突检查在一个事务里**，顶班的班次和维修员名下未完成的工单时间冲突，就整体回滚并提示，不能出现"人请假了但工单还挂在他名下"的脏状态。

回调丢失的兜底有两层：**定时任务每天凌晨拉取最近三天的审批单做对账**，缺的补上，重复的靠幂等键挡掉；另外提供手动触发入口，极端情况随时能补。事件驱动负责实时性，定时对账负责正确性，两条腿走路。

#### Q38：钉钉账号和本地账号怎么绑定？

**答**：首次使用走一次绑定：用户在钉钉里扫码或点击授权，我们拿到钉钉的用户标识，和本地账号建立映射，之后所有事件里的钉钉用户都能解析成本地身份。

这个映射是所有钉钉能力的身份基础——机器人问答要按人做权限过滤，卡片按钮要校验操作权限，审批同步要找到对应的本地员工记录。**映射找不到的用户，审批同步会自动创建基础账号**，保证业务不断在身份这一环，创建出来的账号等管理员后续完善信息。

### 模块五：系统稳定性与部署

#### Q39：模型推理为什么要独立服务化？为什么用 vLLM？

**答**：先说为什么独立。Embedding 和 Reranker 是检索链路的高频依赖，问答、知识入库、去重判断都要调。如果和主应用混在一个进程里，一是模型加载把启动时间拉到分钟级，二是资源互相干扰，三是**换模型要动主应用**。

独立成推理服务后，对外是 OpenAI 兼容接口，主应用只认接口不认模型——**换模型、升级版本，改部署配置就行，业务代码零改动**。这个解耦我们实际受益过，模型迭代的时候业务侧完全无感。

vLLM 的选择要分两层说：它最初是为生成式推理设计的，PagedAttention 这类核心优化只适用于逐 token 生成；但从服务化能力看，它已经扩展成通用模型服务框架，支持编码和重排模型的托管。我们统一用它管三类模型，图的是**一个引擎、一套 OpenAI 兼容接口、一套运维**，编码请求还能受益于它的请求拼批和显存调度，比如批量导入工单时的密集向量化请求。服务还带健康检查，加载中、就绪、异常三态分开上报，上游据此决定等还是降级。

**追问：vLLM 不是为生成设计的吗，托管编码模型有什么价值？**
对，PagedAttention 解决的是生成过程中 KV cache 的显存管理，编码模型是单次前向，用不到这个。编码模型受益的是另一组能力：请求级动态拼批、显存统一调度、标准化的服务接口。选型时我们清楚这个边界，选它的核心理由是接口和运维统一，不是追求生成侧优化。将来编码侧真遇到性能瓶颈，可以换成专门的编码推理服务，接口层封装好了，业务代码不用动。

#### Q40：全链路降级是怎么设计的？

**答**：原则是**每一环都有更便宜的替代方案，且切换自动完成**。按依赖从下往上说：

推理服务挂了或者没就绪，检索自动降级成纯关键词召回，问答功能不中断；Reranker 挂了，用规则加权重排替代；检索结果为空，有语义兜底放宽阈值再捞一次；模型分类意图失败，有规则兜底；连大模型本身不可用，系统返回友好提示而不是报错。

恢复也是自动的：降级不是手动开关，是每次调用时探测服务状态，服务恢复下一次调用就自动切回，**不需要人守着**。

设计上我们坚持一点：**降级后的行为必须仍然是正确的**，只是质量下降，绝不能为了"看起来可用"返回错误结果。比如宁可说"没检索到"，也不能降级成编造答案。

#### Q41：你们怎么做效果评估和阈值标定的？

**答**：核心方法是**建验证集、跑回归、看分布**。

验证集从真实工单里挑，覆盖几类典型：正常故障描述、带错误码的查询、英文日志、还有应该被拒绝的无关闲聊。每次改动检索逻辑都全量跑一遍，看两件事：正常查询能不能检到、无关查询有没有被拦住。

阈值标定看分数分布：把验证集的检索分数打出来，相关和不相关的分数之间如果存在真空带，阈值就定在带中间。这个方法比拍脑袋强在**可解释**——每个阈值都能说出它卡在哪两类样本之间。

我们还把标定做成了脚本，知识库内容变了、模型换了，重跑一遍就能看阈值要不要跟着动。评估这件事不是一次性的，是跟着系统演进的常规动作。

#### Q42：部署架构是怎样的？

**答**：整体 Docker Compose 编排，前面 Nginx 做入口。

Nginx 后面两类服务：主应用提供 API 和静态页面，推理服务独立一组容器。数据面是 PostgreSQL、Milvus、Redis 三个有状态服务，数据卷独立挂载，备份策略单独做。

几个考虑：**推理服务和主应用分开扩缩容**，检索压力大时推理服务单独加资源；制造企业在内网，全部私有化部署，数据不出网；配置用环境变量注入，同一套镜像多环境复用。前端构建产物直接由主应用托管，少一个部署单元。

#### Q43：流式输出为什么用 SSE 而不是 WebSocket？

**答**：我们的流式场景是**单向的**：服务端把回答逐段推给前端，推完结束，不需要双向通信。SSE 就是为这个场景设计的：基于普通 HTTP，天然走现有的网关和反向代理，断线浏览器自动重连，实现和运维都简单。

WebSocket 是双向全双工，能力更强但代价也高：要自己处理心跳、重连、连接状态，代理层配置也麻烦。**场景是单向推送却用双向通道，是过度设计**。

我们真正需要双向的场景在钉钉侧——卡片按钮点击后要有响应，那个走的是钉钉的回调通道，职责清晰，各用各的。

### 模块六：模型选型

#### Q44：为什么选 Qwen3-Embedding-8B？和 bge-m3 比优势在哪？

**答**：选型时主要对比了 bge-m3 和 Qwen3-Embedding 系列，最终选 Qwen3-Embedding-8B，四个理由：

**第一，跨语言能力是我们的硬需求**。知识库是中文的，但设备日志是英文的，跨语言检索不是加分项是及格线。Qwen3-Embedding 原生支持一百多种语言，中英跨语言对齐是它的基本盘，这一点在我们的英文日志检索场景实测优势明显。

**第二，效果基准领先**。在 MTEB 多语言榜单上，Qwen3-Embedding-8B 排在开源模型前列，明显高于 bge-m3 的分数段；中文子榜表现也强。当然榜单只是入围依据，最终我们是拿自己的验证集跑过才定的——这也呼应我们的评估方法，**看榜不如看自己的数据**。

**第三，生态一致性**。Reranker 用的是同系列的 Qwen3-Reranker，同一家族的编码模型和重排模型在语义空间的刻画上更一致，粗排圈出来的候选精排接得住，两阶段的衔接更顺。

**第四，可变维度**。它支持 Matryoshka 表征，向量维度可以按存储预算裁剪。我们用降维后的 1024 维入库，效果和存储的平衡点刚好，将来库规模上去了还能再降。

**为什么选 8B 而不是更小的规格**：检索是问答的地基，召回上限由 Embedding 决定，精排救不回没召回的东西，所以召回这一环我们愿意给足配置。编码只在检索和入库时发生，不像生成模型每个字都要过模型，成本完全可控。反过来精排我们用了轻量版，就是"召回给足、精排要快"的分工。

#### Q45：Qwen3-Embedding 支持稀疏向量，为什么还要单独走 BM25？

**答**：理论上用它的稀疏输出做混合检索是可以的，但我们最终用数据库的关键词检索做字面召回这一路，两个原因：

一是**确定性路径的可控性**。错误码精确匹配这种场景，我要的是等值查询的确定性，不是稀疏向量的近似匹配。数据库的精确查询结果是 100% 可解释的，出了问题好排查。

二是**工程复杂度**。稀疏向量方案意味着所有字面匹配逻辑都要走向量库，索引策略、查询语法都得重新适配；而关键词这一路复用现有的数据库能力，索引建好就是现成的，维护成本几乎为零。

本质上这是个**"不为技术上的统一牺牲工程上的简单"**的决策。两路融合的效果达到了，没必要追求单技术栈的整洁。

#### Q46：Reranker 为什么用轻量版而不是更大的？

**答**：精排在链路里的位置决定了它的约束：**每次问答都要调、延迟直接加在用户等待上**。交叉编码本来就比双塔慢，再上大规格，响应时间用户就有感了。

轻量版的判断能力对我们的场景够用——精排的输入是 RRF 融合后的头部 30 条候选，正确答案基本都在里面，精排的任务是排序不是大海捞针，对模型能力的要求没有召回那么极端。

所以整个模型的配置策略是一句话：**把参数预算花在决定上限的环节，把延迟预算留给决定体验的环节**。召回用大模型保上限，精排用小模型保速度。

#### Q47：有没有考虑过微调 Embedding 模型？后面怎么优化？

**答**：考虑过，但当前阶段没做，原因是**投入产出的判断**。微调需要领域标注数据，我们的验证集规模还在积累中，现阶段通用模型加工程手段——查询清洗、词表映射、混合召回——已经把主要问题解决了，边际收益最高的是继续打磨链路而不是微调。

但架构上是预留好的：推理服务是 OpenAI 兼容接口，**将来换成微调版模型，业务代码零改动**，这就是服务化解耦的价值。

后续优化方向我看有三个：一是随着工单积累，用真实检索日志构造微调数据，做领域适配；二是把用户反馈闭环做起来，回答被采纳还是被忽略，作为检索质量的在线信号；三是高频问题做答案缓存，进一步压延迟。

#### 量化指标被质疑时的通用话术

**原则：不捍卫数字的统计学严谨性，把叙事重心放到工程过程上。**

"这个 85% 不是学术意义上的评测分数，我给您讲它的来历：我们从真实工单里挑了 50 条典型问题构造验证集，一开始命中率只有三成，我们逐条分析失败样例，定位出五个具体问题——英文日志检不到、故障码被当普通词、复合故障语义稀释等——逐个修复，每修一个跑一次回归，最后稳定在八成五。这个数字对我最有价值的部分不是 85 本身，而是**建验证集、定位、修复、回归**这套方法，后面每次改动我们都这么验证。"

#### 绝对不要说的话

- 不报精确延迟数字（80ms、200ms 之类），除非现场实测过
- 不说"全量评测""公开榜单验证"，验证集就是内部 50 条，如实说
- 不说"独立完成"，全程用"参与""我负责的部分是"
- 被问到没做过的东西，直接说"这块我们评估过但当前阶段没做，原因是……"，然后接上优化方向——**诚实加思考比硬编值钱得多**
